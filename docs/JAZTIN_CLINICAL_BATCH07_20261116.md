## Implemented

### Family addition and exact committed-result recovery

`GuardianController` requires a command key, derives the guardian from the current account, prohibits client identity/branch/author overrides, and uses the existing transaction/journal. Patient-code serialization precedes guardian locking and the existing ten-dependent limit check. Person, Patient, active guardian link, administrative audit and original receipt commit together. An audit exception rolls everything back. Same command recovers the original Patient; different commands remain separate additions. No fuzzy identity matching, automatic admission, invitation/claim change or clinical completion.

Original-receipt reads require the original actor/key and current active guardian/link authority. Ended/claimed links and foreign actors do not reveal the receipt; account revocation is rechecked before replay. The existing preferred branch inheritance and Other trim/clear behavior remain unchanged. No migration.

The existing Family screen now has explicit loading/error/retry states, exact guardian capability checks, frozen original intent, same-tick dispatch protection, pending/unconfirmed feedback and authoritative Patient-code confirmation. A retry uses the original key/body. Only an opaque actor/guardian-scoped key is persisted in sessionStorage; reload restores **read-only** receipt recovery without storing child details. If the original draft is lost and no committed receipt is found, the UI stays unconfirmed rather than silently issuing another creation. A new authenticated session can read the original server receipt using its exact key. Primary addition controls are 46px high; no general redesign.

Actual routes/fields/statuses and compatibility: [Dependent creation v1](contracts/DEPENDENT_CREATION_API_V1.md). Owned API-client and Family callers updated; old test callers receive explicit keys without weakening existing expectations. Older servers remain readable but new additions are unavailable without the safety capability.

### Exact-context message search/history readback

The existing authorized message endpoint emits context for ordinary, older, search, newer and empty reads. Inbox and message responses are private/no-store. The shared client checks exact conversation/Patient/branch proof before adopting rows; missing/mismatched proof is an error. Existing auth/request/query/selection/access-version guards remain in effect. A separate 30-second read deadline preserves the existing single polling/refresh mechanism; no new polling or blind retry loop.

Encrypted-history keyword/contact search, bounded page scans, cursor scope, literal React highlighting and empty-state behavior are retained. No body is added to inbox summaries. No sending, closed-state transition, active-Dentist switching, notifications, invitation mail, workforce or operational archive behavior changed. [Message read context v1](contracts/MESSAGE_READ_CONTEXT_API_V1.md) records the compatible frontend/backend rollout requirement.
