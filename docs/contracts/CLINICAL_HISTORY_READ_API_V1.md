# Clinical history read API v1 — implemented 2026-11-16 Asia/Manila

Clinical owner Jaztin; additive reads, no new clinical permission or transition.

`GET /api/treatments?patient_id=<Patient-public-ULID>&status=Completed&page=1&per_page=20` filters the **existing authorized Treatment::visibleTo actor scope** to that exact Patient. Without date/from/to, this exact-Patient query reads Completed history across dates, newest started_at/internal-id first, with ordinary Laravel pagination (`data`, `meta.current_page/last_page/total`, links). Per-page remains 1–100. A contradictory In Treatment filter without a date window returns 422; arbitrary foreign/unknown Patient IDs do not broaden scope. Without patient_id the existing default current-day/date-window behavior is unchanged. Explicit from/to are paired, at most 184 days, and narrow the scope as before.

`GET /api/treatments/{treatment-public-ULID}` remains the authoritative detail, with exact Patient, branch, Visit, queue if present, appointment or null, responsible/authoring Dentist, status/revision, procedures and history. No-store headers now protect index/detail/Patient safe-history responses. No automatic encounter/Visit/queue creation, assignment or treatment transition occurs on reads.

Existing authorization: authoring Dentist can read their own record; a Dentist currently treating a Patient on an active Visit can read that Patient's earlier Completed Treatments but cannot edit another Dentist's record. When that continuity grant ends, a new detail/list request must deny/omit the record. Staff reads only permitted branches; Owner gets operational summary without clinical text; Patient uses only `/api/treatments/mine` safe completed subset. Per-revision clinical snapshots remain author-only. No handover grant, Patient raw encounter access or new medical-alert field is introduced.

The existing Patient Records Clinical tab now fetches this paginated history independently of the current queue's loaded date window. One review action opens exact server detail, strictly Patient/encounter-matched and read-only. New/old request lifetimes and auth generation are checked. Current chart is separately labelled and read-only from this view; it is not an as-of-encounter reconstruction. Historical entries keep dates and exact encounter references. Earlier-care links preserve a return to the original encounter, without fabricating an appointment for walk-ins.

Patient Historical records still uses its permitted appointments, treatment summaries, prescriptions and invoices APIs. It now retries failed reads, follows invoice cursors, rejects malformed/foreign invoice contexts, fails visibly on later-page errors, keeps safe summaries separate instead of matching by date, and links exact persisted receipts to Billing. Timeouts/obsolete readers stop additional page dispatch. Reads do not settle an invoice or generate a new receipt. All PDF readers can suppress late downloads after account/navigation changes.

Shared-file dependencies: API client and Patient Portal; clinical Patients/EncounterCare; existing TreatmentController read additions. No routes, migrations, roles, shared middleware, roster authority or notification behavior changes in Batch06.
