# Dependent creation and recovery — v1 (implemented)

Clinical/Patient ownership, 2026-11-16 Asia/Manila. This completes recovery of the existing Family addition; it introduces no admission, duplicate-name matching, invitation or guardianship policy. Deployment/integration acceptance is separate.

* `GET /api/me/dependents`: current authorized active dependent links, existing resource fields plus `last_name`. `meta.me.id` is the signed-in guardian Patient ULID. `meta.creation_contract = {version:1,idempotency:true,durable_recovery:true}` permits this client to add. An older target remains readable; the new UI disables additions without this capability.
* `POST /api/me/dependents`: **required `Idempotency-Key`**, existing `{first_name,last_name,date_of_birth,sex?,relationship,relationship_other?,consent}`. Names/relationship are validated strings; DOB is `Y-m-d`, not future, consent accepted. `Other` requires nonblank Specify; existing service trims it and clears it for another relationship. Patient/guardian/branch/author/revision overrides are prohibited. The existing adult guardian requirement and maximum ten active dependents remain authoritative.
* `201 {data:{id,code,name,first_name,last_name,date_of_birth,relationship,relationship_other,minor,age,has_account},meta:{dependent_receipt:{guardian_id,dependent_id,link_id}}}`. Public IDs identify the exact Patient and guardian link; Patient code is generated by the existing service. Creation has no appointment, Visit or encounter. The existing service inherits the guardian’s preferred branch; the caller cannot assign or override it.
* `GET /api/me/dependents/creation-receipt`, same required header: `200` with the original creation response. It is a **read**, never creates a Patient and does not imply that the original snapshot is current Family status. Reload the Family list for current links.

The `patient.dependent.create` command journal is unique by actor/key. Fingerprint includes exact guardian identity and validated original body. Same actor/key/body returns the original 201; changed body/key use is 422. Authorization is checked before replay/work and before disclosure: active verified Patient account, current person/auth version, exact guardian and still-active original dependent link. Foreign actor/key or ended/claimed original link returns 404; revoked account 403. Missing key/invalid data/existing limit returns 422. Existing route middleware owns 401/429 behavior. Reads and creation replies are private/no-store.

Within the existing idempotent transaction, Patient-code serialization precedes the guardian row lock and current authority/limit checks. Person, Patient, guardian link, `patient.guardian_linked` audit and receipt commit or roll back together. Same-key contention returns one Patient; two different commands remain separate additions (no unsafe fuzzy deduplication). The tenth-slot race admits at most one addition. **No schema or migration change.**

The owned React caller freezes the original body/key, prevents duplicate dispatch, bounds requests at 30 seconds, rejects wrong guardian/child/link receipts and stale auth lifetimes. A network or malformed response remains unconfirmed. Retry in the same mounted form uses the identical original command. Only an opaque actor/guardian-scoped key is stored in sessionStorage; no child name, DOB or relationship draft is persisted there. Reload restores read-only receipt recovery. If the request never committed and its draft has been lost, a 404 does not prove failure: this client stays unconfirmed rather than creating another Patient. Closing/clearing browser storage is not durable server cancellation. Account invitation and claim behavior are unchanged and were not exercised with live mail.
