# Notification history API v1 — Joevan, 2026-11-15

Continuation revision: recipient archival is implemented and focused PostgreSQL/browser acceptance has executed on Joevan's private Linux runtime. No retention periods, restore, hard-delete, clinical or provider changes.

- `GET /api/notifications`: authenticated recipient's newest50 active inbox rows, descending existing insertion ID. Rows retain `{id,kind,title,body,target,created_at,read}` and add `{archived,archived_at}`; timestamps use the Manila offset.
- Optional `?before=<public notification ULID>` fetches up to 50 strictly older rows. Cursor lookup is limited to the signed-in recipient, including Owner. Invalid ULID:422 `{message,errors}`; missing or another recipient's cursor:404. Caller-supplied user/branch cannot widen visibility.
- Optional `?collection=active|archived`, default active. Metadata: `{unread,has_more,next_before,collection,archive_available}`. `unread` is the current active inbox unread total, independent of pagination; archived items retain their actual read state separately. `next_before` is the last row's public ID when more rows exist, otherwise null. A newer insert does not shift older cursor pages. An anchor archived since the previous page remains resolvable inside recipient scope; selection filters the requested collection after applying that immutable ID boundary.
- `POST /api/notifications/{id}/read`: existing recipient-only idempotent update, preserving the first read timestamp. Returns the latest first-page response and `meta.read_id` identifying the exact confirmed target, which can be older than that page. Another recipient's ID:404. No revision/operation UUID is required for this monotonic transition.
- `POST /api/notifications/read-all`: recipient-only, repeat-safe active inbox transition and current first-page readback. Archived read evidence is unchanged.
- `POST /api/notifications/{id}/archive`: authenticated recipient only, including Owner (no global inbox access). Inserts one immutable archive event under actor/notification locks, with a unique notification primary key and database-assigned timestamp. Repeats recover the same timestamp without another audit entry. Does not mark the notification read or delete content. Response is the active inbox page plus `meta.archive_receipt:{id,archived:true,archived_at,replayed}`. Wrong recipient/missing ID:404; revoked actor:403. The archive/audit transaction rolls back together. Concurrent read and archive preserve both transitions.
- Capability gate: the additive `database/operations/2026_11_18_000100_create_notification_archives.php` extension is opt-in on the private provisioning profile (`--operations`). Without the table, `archive_available:false`; existing active reads work, archive requests or archived reads return503 `notification_archive_unavailable`. A route's existence alone is not capability evidence. No default deployment migration chain is changed.

The Staff/Dentist/Owner shell can load older pages, select Inbox/Archived notifications and archive an exact item. It waits for the exact archive receipt before completion. Uncertain archive responses retain the target for Retry archive; replay is safe. Collection switches invalidate obsolete responses; failure never becomes an empty-success claim. Existing account/auth-generation/unmount guards remain. A successful mutation refreshes its first page. The separate Patient portal is unchanged and uses its existing recent active window.

GEN-10's non-destructive notification archival is implemented; broader GEN-11 clinical archive/restore permissions remain separate and unchanged. No universal Owner access, restore route or retention job is introduced. The append-only archive table refuses update/delete/truncate; rollback refuses to drop recorded history.
