# Patient receipt navigation API v1 — implemented, 2026-11-16 Asia/Manila

Read/navigation additions only, Clinical owner Jaztin. Existing invoice issue, synthetic at-clinic Cash settlement, receipt creation, authorization and PDF generation remain unchanged. No payment provider or messaging action is introduced.

* `GET /api/invoices/mine?appointment_id=<appointment-public-ULID>&per_page=25&cursor=<invoice-public-ULID>` adds optional exact appointment filtering to the existing Patient/authorized dependent scope. `appointment_id` must be 26 characters; branch/Patient identity substitutions remain prohibited. Visit Patient must match Invoice Patient, and appointment Patient must match Visit Patient. Response uses existing `{data:[InvoiceResource],meta:{per_page,next_cursor}}`; private/no-store. Existing status/keyset filtering is retained. No match means no authorized invoice returned, not proof of payment or nonexistence.
* Existing InvoiceResource adds `appointment_id` (actual Visit appointment public ULID or null), `visit_source` (`appointment`/`walk_in` or null for legacy invoices without Visit), `visit_date` (Manila clinic date or null). Existing `visit_id`, `treatment_id`, Patient, branch, revision, monetary amounts, payment and persisted receipt identities remain intact.
* Existing `GET /api/invoices/{invoice-public-ULID}/pdf` and `/receipt-pdf` remain authorized no-store PDF downloads. New headers: `X-Invoice-Id`, `X-Patient-Id`; receipt PDF also `X-Receipt-Id`. They identify existing records, never create them. Inaccessible/unavailable documents return 404. CORS exposes only these additional response headers and Content-Disposition; existing audit-export headers, origins, credentials and allowed methods remain unchanged.

The Patient portal preserves exact identities through Completed/Checked-In/In-Treatment appointment → Invoice and receipt → Return to appointment. One matching confirmed receipt expands automatically. General Billing retains walk-in receipts without fake appointment links. Reload/new sign-in uses existing list readback. UI checks own/dependent Patient membership, exact optional appointment/invoice/receipt constraints, status and monetary proof; a `Paid` label alone is insufficient for a confirmed receipt. Invalid/malformed reads fail visibly; a failed load is not an empty list. Request lifetimes, auth generations, bounded reads, pagination/refresh generations and PDF adoption checks prevent stale responses. PDF bytes are downloaded only after matching the expected invoice/Patient/receipt headers; missing identity headers on an older target fail safely. There is no automatic financial mutation or retrying payment when viewing a receipt. Existing explicit Review and pay / Resend controls are preserved; browser acceptance does not invoke them.

No schema, route, roster, financial command, PDF renderer or historical-record changes. Version is this additive read contract, not a replacement payment API. Evidence, original-QA attribution limits and shared-file overlap are in [Batch 05](../JAZTIN_CLINICAL_BATCH05_20261116.md).
